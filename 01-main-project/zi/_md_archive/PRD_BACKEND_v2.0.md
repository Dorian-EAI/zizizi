## 3. 统一账号、双角色与权限

### 3.1 身份模型

**[目标]** 同一自然人账号可以同时拥有 `user`（客户）与 `worker`（师傅）身份；`admin` 是独立 Web 管理主体，不得混入双角色账号。

后端必须表达以下稳定语义，具体表名可由数据库设计确定：

- `account_id`：同一登录身份的稳定主键，负责登录凭据、手机号、账号安全、隐私授权和注销状态。
- 用户档案：以 `account_id` 一对一关联客户资料、地址、会员和客户侧资产。
- 师傅档案：以 `account_id` 一对一关联认证、技能、服务区域、培训、保证金和师傅侧资产。
- `active_role`：本次会话/令牌正在使用的角色，不代表账号只拥有该角色。
- `role_availability`：每个角色的可用状态，例如可进入、需开通、审核中、已受限，并携带可修复的阻断项。

统一身份主键可以通过新增 `accounts` 表或等价映射实现；这里规定的是业务语义，不承诺具体表名。

### 3.2 登录与角色切换

**[现状]** 用户登录和师傅登录分别查询 `users.openid` 与 `workers.openid`；两表可以出现同一 `openid`，但没有外键关联。`POST /api/auth/switch-role` 当前只修改 `User.role`。

**[目标]** 登录和切换必须满足：

角色切换是在同一账号登录会话内更换 `active_role`，**不是登出，也不要求用户重新完成微信登录**；账号级登录态保持有效，服务端只更新并签发受目标角色约束的上下文。

客户端稳定入口文案固定为：用户端“我的 > 切换到师傅工作台”、师傅端“我的 > 切换到找服务”；没有师傅档案时显示“我的 > 申请成为师傅”。后端返回的角色可用状态、阻断原因和继续办理目标必须足以支持这三条入口，但不得把界面文案当作鉴权条件。

1. 微信身份先解析到唯一 `account_id`，再读取其角色档案。
2. 切换到师傅角色前检查师傅档案是否存在；不存在时返回“需开通师傅身份”的明确状态和继续开通入口语义，不得伪装切换成功。
3. 切换成功后签发或刷新带 `account_id`、`active_role`、角色主体 ID 和令牌版本的角色上下文；不能继续使用客户令牌调用师傅接口。
4. 切换角色不取消进行中订单、不清空草稿、不停止已启动的位置会话，也不改变资金状态。
5. 有未提交表单、位置上报或资金操作处理中时，响应应能让客户端展示影响说明；切换完成后建立目标角色的新导航栈，返回键不得跨回旧角色页面。
6. 账号停用作用于全部普通角色；仅师傅资格受限时，客户角色仍可使用。

### 3.3 数据共享与隔离

| 数据 | 共享/隔离规则 |
|---|---|
| 登录凭据、手机号、账号安全、隐私授权 | 账号级共享 |
| 客户订单、地址、优惠券、客户钱包视图、未读数 | 用户角色隔离 |
| 师傅报价、工作订单、资格、培训、收入、保证金、未读数 | 师傅角色隔离 |
| 进行中订单 | 按订单中的 `user_profile_id` / `worker_profile_id` 授权，不因当前账号同时拥有另一角色而越权 |
| 管理员数据 | 与普通账号完全隔离，使用独立认证与权限体系 |

### 3.4 授权决策

每次敏感操作都必须由服务端按以下顺序重新判断：

1. 令牌有效、未注销、未被拉黑；
2. `active_role` 与动作要求一致；
3. 角色档案存在且允许执行该类动作；
4. 当前主体拥有或被指派到目标对象；
5. 对象版本和多轴状态允许迁移；
6. 动作特定资格、金额、定位或风控条件满足。

前端隐藏按钮不能替代授权。任何拒绝都返回稳定 `reason_code`、面向用户的说明、当前对象版本，以及可修复时的 `repair_target` / 缺失项；不得只返回“无权限”。

## 4. 订单多轴状态契约

### 4.1 四个正交状态轴

**[目标]** 订单聚合至少同时返回以下四轴，字段名以产品交互文档为准：

| 状态轴 | 允许值 | 负责的问题 |
|---|---|---|
| `service_state` | `pending / accepted / departing / arrived / serving / completed / reviewed / cancelled / closed` | 维修履约进行到哪一步 |
| `payment_state` | `unpaid / processing / paid / failed / refunding / refunded` | 钱是否已经支付或退回 |
| `aftersale_state` | `none / requested / processing / resolved / rejected / appealing` | 退款、投诉、理赔或申诉进度 |
| `price_adjust_state` | `none / pending / accepted / rejected` | 服务中差价是否已确认 |

四轴不能互相覆盖。例如退款处理中仍保留原 `service_state`，差价待确认时仍保持 `service_state=serving`。

页面需要的单一“主状态”由服务端或共享规则按以下优先级投影：

`售后处理中 > 支付异常/退款中 > 待某方操作的履约状态 > 普通履约状态`

主状态是展示投影，不是第五条业务状态轴，不得回写覆盖原始状态。

### 4.2 履约迁移与触发方

| 当前 `service_state` | 目标状态 | 唯一业务触发 | 关键前置条件 |
|---|---|---|---|
| `pending` | `accepted` | 用户选中报价 | 报价仍有效；订单未被他人选定；原子锁定报价并指派师傅 |
| `accepted` | `departing` | 中标师傅点击出发 | 师傅拥有该订单；定位预检通过；追踪会话成功创建 |
| `departing` | `arrived` | 中标师傅点击到达 | 到达校验通过，或异常签到流程获准 |
| `arrived` | `serving` | 中标师傅点击开始服务 | 到达记录有效；客户端不得代替触发 |
| `serving` | `completed` | 中标师傅提交完工 | 必需凭证齐全；不存在待确认差价；最终应付可由服务端重算 |
| `completed` | `reviewed` | 用户在支付完成后评价 | `payment_state=paid`；评价写入成功 |
| 允许取消的状态 | `cancelled / closed` | 用户、平台或规则引擎 | 取消规则、责任方和资金后果已确定并留痕 |

用户选中报价后订单直接进入 `accepted`，师傅收到“已接单/待出发”通知；v6.2 不设置第二个“师傅确认接单”状态。

### 4.3 支付、售后与差价规则

- `payment_state` 只能由可信支付结果、退款结果或平台核销推进；客户端回调页面不得直接标记支付成功。
- 支付超时或网络中断时先查询原支付单结果；结果未知时保持 `processing`，不得重复创建业务上等价的支付。
- 售后状态变化不删除履约时间线、报价快照、资金明细或证据。
- 差价只能由中标师傅在服务中发起；用户明确接受后，单条差价记录由当前实现的 `approved` 迁移为目标语义 `accepted`。
- 差价待确认时不得完工结算。超时不得自动同意、自动扣款或静默改为成功；v6.2 默认保持“待协商”，同时提供联系对方和客服的能力。
- `price_adjust_state` 是摘要：无记录为 `none`；存在未处理记录时为 `pending`；否则反映最近一条已处理申请。最终应付必须逐条汇总所有已接受记录，不能只看摘要状态。

### 4.4 金额唯一来源

**[目标]** 最终应付由服务端按不可变组成项计算：

`中标报价 + 已接受差价 + 明示附加项 - 有效优惠/抵扣 = 最终应付`

- 完工请求不得接收可覆盖 `final_price` 的自由金额；即使为了旧客户端兼容暂时保留该字段，也必须忽略或与服务端重算结果严格相等，否则拒绝。
- 所有金额在计算与持久化边界统一使用最小货币单位整数或无浮点误差的 Decimal；当前“订单金额按元、差价按分”的混用必须在迁移和测试中显式校验。
- 中标时固化报价、平台费率来源和预计到手快照；师傅后续等级变化不追溯修改已中标订单。

## 5. `allowed_actions` 与可解释操作

### 5.1 订单投影最小契约

**[目标]** 所有订单详情，以及会直接渲染主操作的列表卡片，至少返回：

```json
{
  "order_id": 123,
  "order_version": 12,
  "event_version": 37,
  "active_role": "worker",
  "states": {
    "service_state": "arrived",
    "payment_state": "unpaid",
    "aftersale_state": "none",
    "price_adjust_state": "none"
  },
  "primary_action": "start_service",
  "allowed_actions": [
    {"action": "start_service", "requires_idempotency_key": true},
    {"action": "contact_customer", "requires_idempotency_key": false}
  ],
  "blocked_actions": [
    {
      "action": "complete_service",
      "reason_code": "SERVICE_NOT_STARTED",
      "message": "开始服务后才能提交完工",
      "missing_requirements": ["service_state=serving"],
      "repair_target": "start_service"
    }
  ]
}
```

示例表达目标响应语义，不代表当前接口已包含这些字段，也不规定 URL。

### 5.2 生成规则

- `allowed_actions` 由服务端根据账号、角色、对象归属、四轴状态、资格、风控和最新版本实时生成。
- `primary_action` 必须是 `allowed_actions` 中的一个动作；每个角色同一时刻最多一个主操作。
- `blocked_actions` 仅包含该角色看得见且可修复/需解释的动作，不泄露管理员能力或他人权限。
- 动作描述可用于呈现，但不能作为授权凭证；提交时必须再次校验。
- 状态冲突返回最新四轴状态、最新版本和 `refresh_required=true`，客户端关闭旧弹窗并刷新，不继续执行陈旧动作。

### 5.3 核心动作矩阵

| 场景 | 客户主要动作 | 师傅主要动作 | 常见阻断 |
|---|---|---|---|
| `pending` | 查看/选择报价、取消 | 提交或查看报价 | 资格缺失、报价截止、订单已更新 |
| `accepted` | 查看师傅与预约 | 出发 | 非中标师傅、定位不可用、版本冲突 |
| `departing` | 查看实时位置 | 到达 | 会话陈旧、到达校验失败 |
| `arrived` | 查看服务准备 | 开始服务 | 到达记录无效、账号被安全硬阻断 |
| `serving` | 处理差价、查看进度 | 申请差价或完工 | 差价待确认、凭证缺失 |
| `completed + unpaid` | 确认费用并支付 | 查看待收款 | 支付结果处理中、金额版本变化 |
| `paid` | 评价、发票、售后 | 查看入账 | 售后冻结、结算等待期 |
| 售后处理中 | 查看/补材料 | 查看/补材料 | 当前责任方不是本人、材料不完整 |

## 6. 报价生命周期与选定规则

### 6.1 报价状态

**[目标]** 报价至少支持：

`draft → submitted → selected / not_selected / expired / withdrawn`

- `draft`：未提交草稿；是否服务端保存由接口设计决定，但一旦返回给多端就必须有版本。
- `submitted`：用户可见、等待选定；截止前是否允许修改由服务端返回，不由客户端硬编码。
- `selected`：唯一中标报价，终态。
- `not_selected`：其他报价在某报价中标后进入该终态。
- `expired`：报价截止、订单取消/关闭或规则失效导致不可再选。
- `withdrawn`：师傅在允许窗口内主动撤回；已中标后不得撤回。

每条报价拥有稳定 ID、报价版本、状态更新时间和截止时间；同一订单同一师傅的有效报价必须唯一。修改报价使用同一业务对象的新版本，不能通过重复创建绕过唯一性和频控。

### 6.2 选定报价的原子事务

选定动作必须在一个事务中完成：

1. 校验客户拥有订单、订单仍为 `pending`、请求基于最新订单/报价版本；
2. 锁定订单及候选报价，确认报价为 `submitted` 且未过期；
3. 将目标报价改为 `selected`，其余有效报价改为 `not_selected`；
4. 写入订单师傅、报价金额、费率和价格快照；
5. 将 `service_state` 从 `pending` CAS 到 `accepted`；
6. 在同一事务内记录领域事件/发件箱事件，提交后再发送站内与订阅消息。

任何一步失败都不得留下“报价已中标但订单未指派”或“订单已接单但没有中标报价”的半状态。重复请求返回第一次成功结果；并发选择只有一个成功，其余返回最新状态和冲突原因。

### 6.3 报价可见信息

- 中标前师傅只看大致区域、距离、预约时间、服务类目和必要故障信息；精确地址、门牌和联系电话必须遮罩。
- 报价页同时返回客户支付构成、平台服务费率来源和预计到手金额；示例费率不得作为代码常量。
- 用户可比较师傅公开资料、报价、ETA、服务数与统一计算的等级；不得暴露证件原图、内部风控分或其他师傅私密信息。

## 7. 师傅资格与动作级准入

### 7.1 资格不是单一开关

**[目标]** 服务端以动作维度返回资格结果，至少区分：

- `can_enter_worker_workspace`
- `can_view_order_summary`
- `can_bid`
- `can_depart`
- `can_start_service`
- `can_complete_service`
- `can_withdraw`

每项包含布尔结果、稳定阻断码、缺失条件、可修复入口语义、预计处理说明；客户端不得用一个 `is_certified` 推导全部能力。

### 7.2 校验维度

| 动作 | 必须检查的维度 |
|---|---|
| 浏览接单大厅 | 已登录并进入师傅身份；未开通者可看开通说明，但订单敏感信息必须遮罩 |
| 提交报价 | 账号正常、实名有效、订单类目资质通过、必修培训完成、服务区域匹配、保证金/保障等级满足、当日额度与并发任务上限允许、订单与报价仍有效 |
| 出发 | 本人已中标、订单为 `accepted`、位置上报能力可用；定位权限只在此处成为硬前置 |
| 开始服务 | 订单为 `arrived`，到达校验或获准的异常签到有效 |
| 完工 | 订单为 `serving`，凭证完整且没有 `price_adjust_state=pending` |
| 提现 | 实名有效、有 `available` 金额、到账方式有效、对应金额未被风险/售后冻结 |

资格策略由服务端配置和规则版本驱动，保证金金额、日单量、类目证书和培训课程不得散落在客户端常量中。资格结果需要携带 `policy_version`，以便解释规则变化。

### 7.3 存量任务保护

- 资质过期、保证金不足或账号一般受限，默认只阻止新报价，不得让已有订单、钱包查询、客服和申诉入口消失。
- 只有法律、安全或平台明确的硬阻断才能暂停存量履约；必须记录原因、责任方、恢复条件并通知订单双方。
- 师傅资格变化不能追溯改写已中标报价的费率快照。

**[现状缺口]** 当前 `Worker`、保证金和培训模型已存有部分判断所需数据，但 `create_bidding` 尚未调用统一资格服务；可接单列表也未返回动作级资格与阻断原因。

## 8. 订单级位置追踪会话

### 8.1 会话边界

**[目标]** 位置上报绑定订单行程，而不是绑定页面或仅绑定“师傅当前坐标”。每次出发创建唯一追踪会话，至少包含：

- `tracking_session_id`、`order_id`、`worker_profile_id`
- `session_state`：`active / stale / stopped`
- `session_version`、最后接受的 `sequence`
- `started_at`、`last_reported_at`、`stopped_at`
- `stop_reason`：正常到达、订单取消、平台终止、账号安全阻断等
- 服务端下发的建议上报间隔和陈旧阈值

具体表名和接口路径不在本文预设，但所有上报、查询和停止动作必须校验会话与订单的一致性。

### 8.2 启停与上报规则

1. 师傅点击出发前完成定位用途说明和权限预检。
2. `accepted → departing` 与追踪会话创建应在同一业务事务内完成；创建失败不得把订单留在“出发中但无法追踪”。
3. 上报携带会话标识和单调递增 `sequence`；重复序号幂等，旧序号不能覆盖新位置，其他订单/师傅的会话一律拒绝。
4. 打开系统导航、拨打电话、切前后台或离开追踪页不结束会话；回到前台后按产品规则恢复并校准。
5. 默认超过 60 秒无新位置标为 `stale`：客户端停止展示不可靠 ETA，并向双方提供重试、去设置、联系对方和客服。
6. 到达、取消或平台终止时停止会话并记录原因；历史点只按授权与留存策略可查，不能继续作为实时位置返回。

### 8.3 隐私与访问

- 仅订单客户、中标师傅和具备工单权限的管理员可查看对应行程；管理员查看也必须审计。
- 中标前不得返回精确位置、精确地址或可反推出住所的轨迹。
- 轨迹响应按用途最小化：实时跟踪只给完成体验所需的坐标、时间、ETA 与陈旧状态；导出、批量查询和长期留存需要更高权限。
- 取消/结束后的留存时长由隐私与争议处理政策统一配置，未评审前不得在代码中写永久保留。

**[现状缺口]** 当前 `WorkerLiveLocation` 每个师傅只有一条覆盖记录，`LocationHistory` 通过可空 `order_id` 关联，缺少会话 ID、序号和停止原因；到达后也没有完整的会话终止记录。

## 9. 支付、结算与资金桶

### 9.1 资金事实与不可变明细

**[目标]** 客户支付成功后生成不可变结算快照，至少列明：

- 中标报价；
- 每笔已接受差价；
- 优惠金额及承担方；
- 客户实付；
- 平台服务费率、规则版本和费用；
- 师傅预计净收入；
- 已发生退款、扣款、冲正；
- 当前资金桶、预计可提现时间和关联售后。

原始资金事实采用追加流水/分录记录；纠错通过冲正和新分录完成，不直接修改旧成功流水。展示余额是分录汇总或经校验的快照，不是唯一账本。

### 9.2 师傅收入资金桶

| 资金桶 | 含义 | 允许动作 |
|---|---|---|
| `pending_settlement` | 客户已支付，处于结算等待期 | 查看组成和预计时间 |
| `available` | 已结算且可提现 | 发起提现 |
| `frozen` | 因售后、风控或争议冻结 | 查看原因、补材料、申诉 |
| `withdrawing` | 已提交提现，结果处理中 | 查询原申请，不可重复申请同一金额 |
| `withdrawn` | 已成功到账 | 查看到账凭证 |
| `reversed` | 退款、扣款或冲正 | 查看关联订单/售后与计算依据 |

保证金账户与收入钱包语义分离；保证金冻结/退还不得伪装成收入资金桶变化。v6.2 不开放师傅收入钱包充值或师傅间转账；文中的“充值”仅指用户余额充值或独立保证金缴纳，不能写入师傅可提现收入。

### 9.3 资金不变量

- 任一支付/退款/提现渠道流水号全局唯一，同一回调重复到达只能产生一次业务效果。
- 支付金额必须等于服务器端当前价格快照；回调金额、币种、商户号和业务单号均需校验。
- 同一订单不得重复结算；部分退款的累计值不得超过原支付金额。
- `available` 扣减与提现申请创建必须原子完成；提现失败释放原冻结金额，不创建第二笔申请。
- 评价完成与否不决定结算；结算等待、售后冻结和风控规则分别表达。
- 资金结果未知时返回“处理中/结果未知”并提供查询原交易的语义，不得把网络超时当作失败后直接重试扣款。

**[现状]** `PaymentOrder.transaction_id`、`RefundOrder.refund_id` 有唯一约束，微信支付成功处理已有重复回调与金额校验测试。**[目标缺口]** 普通充值、支付、提现、退款请求尚未共享统一幂等存储；用户/师傅仍以单一 `balance` 为主，也没有完整资金桶分录。

## 10. 幂等、并发与事件版本

### 10.1 写操作幂等

**[目标]** 发布订单、提交/修改报价、选报价、状态迁移、差价处理、支付、用户余额充值/保证金缴纳、退款、提现、认证提交、售后和关键消息已读等写操作必须携带幂等标识。推荐使用标准 `Idempotency-Key` 请求头；若最终接口采用等价字段，OpenAPI 必须统一说明。

服务端幂等记录至少包含：

- 账号/角色主体、业务操作、幂等键；
- 请求内容指纹；
- 业务对象 ID；
- 处理状态、响应状态码和可安全重放的响应摘要；
- 创建、完成和失效时间。

同一主体、同一操作、同一幂等键：

- 请求内容相同：处理中返回原处理状态，已完成返回第一次结果；
- 请求内容不同：返回冲突，禁止复用键覆盖原请求；
- 数据库唯一约束必须兜住并发窗口，不能只依赖进程内缓存。

幂等记录保留时间按业务风险配置，资金类不得短于渠道可重放/查询窗口。

### 10.2 对象版本与 CAS

- 订单、报价、差价、售后任务、支付/提现任务均拥有单调递增的对象版本。
- 状态写操作携带读取时的预期版本；服务端在同一更新语句/事务内比较并递增版本。
- 版本冲突返回 HTTP 409（或经评审的等价冲突语义）、最新版本、最新状态和刷新提示。
- **[现状]** 订单内部已有 `Order.version` CAS；**[缺口]** 当前 `OrderResponse` 未返回版本，通用状态请求也未要求预期版本，报价/差价等对象未统一版本化。

### 10.3 领域事件

关键事件至少包括账号角色变化、报价提交/选中、订单迁移、差价处理、支付/退款/提现结果、位置会话异常、资格变化和售后变化。

- 每个聚合的 `event_version` 单调递增；消费者忽略小于或等于已处理版本的旧事件。
- 状态更新与事件写入同一事务；跨进程通知使用事务发件箱或等价可靠机制，避免“数据库成功但消息丢失”。
- 事件拥有全局 `event_id`、聚合类型/ID、事件类型、版本、发生时间和最小必要载荷。
- 事件载荷不得包含身份证、完整电话、精确地址、聊天正文、原始证据或整段位置轨迹。

## 11. 消息深链与多端一致性

### 11.1 深链最小载荷

**[目标]** 订单、资金、账号安全和售后站内消息至少携带：

```json
{
  "role": "worker",
  "object_type": "order",
  "object_id": "123",
  "event_version": 37,
  "fallback_route": "worker_orders"
}
```

可选携带不具授权效力的 `pending_action` / 展示摘要；不得在深链中携带精确地址、电话、支付凭据或直接可执行的高风险指令。示例是目标载荷结构，不承诺页面路径名称。

### 11.2 点击与失效兜底

1. 点击消息后先校验登录账号、目标角色、对象权限和对象最新版本。
2. 角色不匹配时说明原因并引导切换；切换成功后继续原目标，而不是跳首页。
3. 消息事件版本落后时进入对象最新详情并提示“状态已更新”，不得展示旧操作。
4. 对象已删除、取消或无权访问时展示可理解原因，并落到 `fallback_route` 对应的稳定功能中心。
5. 目标成功加载后才标记已读；加载失败或需要切换角色时不吞掉未读。
6. 推送仅负责唤回，站内消息是可追溯事实；订阅消息未授权不影响站内可查。

**[现状缺口]** `Message.payload` 当前是自由 JSON，常见载荷只含 `order_id/status`，没有强制 `role/object_type/event_version/fallback_route`，也没有版本校验契约。

## 12. 隐私、安全与审计

### 12.1 最小披露

| 数据 | 目标披露规则 |
|---|---|
| 精确地址、门牌、联系电话 | 报价阶段遮罩；用户选中师傅后，仅订单双方按履约需要可见 |
| 身份证、证书原图、银行卡 | 默认不在普通接口返回；存储加密/令牌化，后台查看需专项权限和审计 |
| 实时坐标与轨迹 | 仅行程相关订单双方及获授权管理员可见；结束后按用途和留存政策降权 |
| 聊天、故障描述、证据 | 仅业务相关主体和获授权客服按工单范围访问；不得进入通用埋点或日志 |
| 账号/风控信息 | 只返回用户完成任务所需的结论和可修复原因，不暴露内部评分规则 |

**[当前高优先级缺口]** 可接单列表使用完整 `OrderResponse`，其中包含 `address`；在中标前必须改为脱敏摘要或角色专用投影。

### 12.2 日志脱敏

- 禁止记录微信登录 `code`、access token、支付密钥、短信验证码、身份证原文、银行卡完整号、聊天正文、证据原图 URL、完整电话、精确地址或原始位置点。
- 手机号只保留必要掩码，OpenID/UnionID 使用不可逆摘要或受控标识；请求体采用字段白名单，不做全量打印。
- 支付/退款日志保留商户业务号、脱敏渠道号、金额、结果码和 `request_id`，不得记录签名材料或通知明文。
- **[现状缺口]** 部分短信服务日志仍可能把手机号作为扩展字段；上线前需统一日志过滤器和回归检查。

### 12.3 持久审计

以下操作必须写不可抵赖的结构化审计记录：

- 角色开通、切换、停用和权限变更；
- 师傅认证、资格、保证金、风控状态变化；
- 管理员查看/导出敏感信息；
- 订单人工改派、强制取消、状态修复；
- 差价、退款、扣款、冻结、解冻、提现审批；
- 售后裁决和证据访问；
- 位置会话的强制启动/终止和轨迹导出。

审计字段至少包括审计 ID、时间、`request_id`、操作者账号/角色/管理员 ID、动作、对象类型/ID、结果、原因码、脱敏前后摘要、来源 IP/设备摘要和策略版本。审计记录不得保存敏感正文或原始精确轨迹；普通应用日志不能替代审计账。

### 12.4 保留、删除与授权

数据保留周期、账号注销、位置/聊天/证据删除与法定争议留存冲突时，必须由统一政策决定并记录执行结果。任何“永久保留”或具体天数在法务和安全评审前都不能作为代码常量。授权撤回后停止未来采集，不得伪装已删除依法必须保留的数据。

## 13. 接口与错误契约原则

### 13.1 当前接口事实

- 认证与角色现状：[`server/app/api/auth.py`](server/app/api/auth.py)、[`server/app/services/auth_service.py`](server/app/services/auth_service.py)
- 订单与报价现状：[`server/app/api/orders.py`](server/app/api/orders.py)、[`server/app/services/order_service.py`](server/app/services/order_service.py)
- 位置现状：[`server/app/api/lbs_track.py`](server/app/api/lbs_track.py)、[`server/app/services/realtime_track_service.py`](server/app/services/realtime_track_service.py)
- 差价现状：[`server/app/api/extra_fee.py`](server/app/api/extra_fee.py)、[`server/app/services/extra_fee_service.py`](server/app/services/extra_fee_service.py)
- 钱包/支付现状：[`server/app/api/wallet.py`](server/app/api/wallet.py)、[`server/app/api/wxpay.py`](server/app/api/wxpay.py)

精确接口路径、方法、鉴权和字段必须从当前 OpenAPI 读取。本文新增的统一账号、状态投影、资格、会话、资金桶、幂等和审计能力是目标契约，不等于已经存在同名接口。

### 13.2 兼容响应

迁移期遵循“先增后改”：

- 新增四轴、版本和动作字段，不立即删除旧 `status`。
- 旧 `status` 仅作为兼容投影，由四轴按明确映射生成；客户端迁移后停止依赖。
- 新字段未准备好时不得返回假值冒充完成；应通过能力版本或明确缺失状态区分。
- 金额响应同时给数值、货币和组成项；禁止让不同页面自行拼出最终应付。
- 列表与详情使用同一状态版本语义；列表可返回摘要，但不能给出比详情更宽的权限。

### 13.3 统一错误

业务错误至少返回：稳定 `reason_code`、用户可读 `message`、`request_id`；与对象状态有关时再返回最新 `object_version`、最新状态和 `refresh_required`。推荐错误码示例：

- `ROLE_PROFILE_MISSING`
- `WORKER_CERT_PENDING`
- `ORDER_VERSION_CONFLICT`
- `BID_EXPIRED`
- `PRICE_ADJUST_PENDING`
- `LOCATION_PERMISSION_REQUIRED`
- `TRACKING_SESSION_STALE`
- `PAYMENT_RESULT_UNKNOWN`
- `IDEMPOTENCY_KEY_REUSED`

错误码名称在 OpenAPI 评审时可调整，但必须保持可机器处理、可解释、可恢复；不能只依赖中文字符串分支。

## 14. 数据迁移与兼容计划

### 14.1 原则

- 所有迁移先在备份恢复的隔离克隆和一次性 MySQL 8 环境验证，再进入维护窗口。
- 优先增加可空字段/新表，完成回填与校验后再加非空、唯一和外键约束。
- 资金与身份迁移必须有逐行对账、异常清单和人工处置通道；不确定数据不得自动猜测合并。
- 生产数据修复使用可审计脚本/迁移，不用 `Base.metadata.create_all`，也不通过无校验 `alembic stamp` 掩盖漂移。

### 14.2 双角色迁移

1. 新增统一账号主键或等价映射，并保留现有 `users.id` / `workers.id` 作为角色档案 ID。
2. 以受信 `openid/unionid` 建立候选关联；存在冲突、空值或一对多时输出异常清单，不自动合并。
3. 回填用户/师傅档案到同一账号，增加唯一约束前先验证重复和孤儿记录。
4. 登录先兼容旧令牌，再逐步签发含账号与角色上下文的新令牌；记录令牌版本以支持撤销。
5. 当角色切换、任务恢复和资产隔离测试通过后，再停用“仅修改 `User.role`”的旧语义。

### 14.3 单状态到四轴

建议的历史初始映射如下；支付单、退款单和售后工单存在时必须覆盖默认值，而不是只看旧订单状态：

| 旧 `Order.status` | `service_state` | 默认 `payment_state` |
|---|---|---|
| `pending` | `pending` | `unpaid` |
| `accepted` | `accepted` | `unpaid` |
| `departing` | `departing` | `unpaid` |
| `arrived` | `arrived` | `unpaid` |
| `serving` | `serving` | `unpaid` |
| `completed` | `completed` | `unpaid` |
| `paid` | `completed` | `paid` |
| `reviewed` | `reviewed` | `paid` |
| `cancelled` | `cancelled` | 依据支付/退款事实回填 |

- `aftersale_state` 从退款、理赔、投诉、工单等事实聚合；无法唯一映射的数据进入人工复核。
- 差价 `approved → accepted`，`pending/rejected` 保持语义；存在多条差价时按第 4.3 节生成摘要。
- 先影子计算四轴并与旧状态对比，再双写，最后让读取切到四轴；不得一次性重写后直接删除旧列。

### 14.4 报价、位置、消息和资金

- `is_selected=true` 的报价回填 `selected`；同订单其他报价在已选中场景回填 `not_selected`；仍在竞价中的未选报价回填 `submitted`；无法判断关闭原因的历史数据按规则标记并留迁移报告。
- 历史轨迹不强行伪造追踪会话；新行程启用会话，旧轨迹以只读历史批次关联，确保来源可解释。
- 旧消息若缺少深链字段，保留原 `payload` 并提供类型级兜底入口；只有新消息强制完整深链，之后再逐批回填可确定对象。
- 单余额迁移到资金桶前先冻结切换窗口并完成“余额、成功流水、支付/退款、提现、保证金”五方对账；差异不得通过调整总余额静默抹平。
- 新旧账本双读校验期间，提现只从一个权威余额来源扣减；禁止双写导致重复入账。

### 14.5 上线顺序

1. 增加结构、版本和审计能力；
2. 回填并输出一致性报告；
3. 服务端影子计算资格、四轴、动作与资金桶；
4. 对内部/灰度账号下发新响应，监控冲突、幂等重放和资金差异；
5. 客户端改为只渲染 `allowed_actions` 并完成深链兜底；
6. 全量切换读取，保留兼容投影；
7. 稳定观察期后再单独评审删除旧字段和旧行为。

资金迁移不建议依赖破坏性数据库 downgrade；回滚以关闭新读写开关、恢复旧读取和前向修复为主，且必须保证新产生的资金事实不丢失。

## 15. 验收与必要测试

### 15.1 业务验收

| 主题 | 必须通过的场景 |
|---|---|
| 双角色 | 同一微信身份同时拥有用户/师傅档案；角色切换后令牌、导航、未读和资产正确隔离；旧角色进行中任务不丢失 |
| 权限 | 非订单方不能访问详情/轨迹/报价；拥有双角色不等于能以另一角色越权；管理员权限独立 |
| 四轴状态 | 支付、退款、售后、差价变化不覆盖履约；主状态优先级稳定；非法和陈旧迁移被拒绝 |
| 动作集合 | 每个角色每种状态得到唯一主动作；阻断动作有原因和修复入口；提交时重新校验 |
| 报价 | 生命周期完整；并发选报价只有一人中标；选中、指派、接单和价格快照原子一致 |
| 资格 | 缺少实名/类目/培训/区域/保障时指出具体缺项；定位只阻止出发；资格过期不隐藏已有订单与申诉 |
| 价格 | 完工不能自由改价；差价待确认阻止完工；已接受差价只计一次；最终应付可逐项解释 |
| 位置 | 会话不随页面退出；重复/乱序点不覆盖最新点；60 秒陈旧降级；结束后停止实时披露 |
| 资金 | 重复支付回调只入账一次；支付/退款/提现超时先查结果；资金桶守恒；提现失败释放原冻结 |
| 消息 | 深链角色正确、旧事件不覆盖新状态、失效对象有落点、加载失败不误标已读 |
| 隐私审计 | 中标前地址/电话遮罩；日志扫描无敏感原文；管理员敏感查看、人工改状态和资金动作均可追溯 |

### 15.2 工程验收

- Alembic 空库升级、ORM 漂移检查、MySQL 8 一次性环境升级和历史克隆回填全部通过。
- 所有状态表/分录表的唯一约束、外键、金额范围和版本 CAS 有并发测试。
- 所有关键写操作有“相同键相同请求”“相同键不同请求”“并发相同键”“超时后重试”四类幂等测试。
- 回放乱序/重复领域事件，最终状态不得回退；事务失败不得产生孤立消息。
- 权限测试覆盖用户、师傅、双角色账号、非订单方、客服、运营、超级管理员及停用主体。
- 日志和审计测试覆盖手机号、身份证、地址、位置、聊天、证据、支付凭据的脱敏/禁止采集。
- 迁移前后逐订单、逐支付单、逐师傅资金守恒，对账差异为零或全部进入有责任人的异常清单。

当前已有测试和目标缺口的运行说明见 [`server/tests/README.md`](server/tests/README.md)。任何 **[目标]** 能力只有在代码、迁移、OpenAPI、客户端联调和上述回归同时完成后，才能标记为已实现。

## 16. 明确不再沿用的旧结论

- 不再用单个订单 `status` 同时表示履约、支付、退款和售后。
- 不再把修改 `User.role` 视为同账号双角色已经完成。
- 不再用 `Bidding.is_selected` 一个布尔值表达完整报价生命周期。
- 不再允许师傅在完工时自由提交最终成交价。
- 不再把单一钱包余额视为完整结算账本。
- 不再让页面自行推导支付、取消、完工等操作；以服务端 `allowed_actions` 为准。
- 不再把推送消息中的自由 JSON 当作可靠深链契约。
- 不再把应用普通日志当作敏感操作审计。
- 不再复制未经代码验证的接口数量、路径和排期作为开发事实。

# 需求完成对照（v6.2）

> **版本与效力**：v6.2，更新日期 2026-08-03。冲突时按 `PRD v6.2`（兼容文件名 `../PRD_v6.0.md`）→ `../docs/design/功能与交互文档.md v6.2` → `../docs/design/样式规范详尽文档.md v6.2` → 后端 v2 规格 / 经评审 API 与数据合同（仅技术字段）→ 本对照 → `pages/` HTML / `zjrnew.design` 的顺序执行。
>
> **证据边界**：HTML、CSS、截图、画布、路由名和组件清单只可作为设计或原型证据，不能单独证明接口已接通、业务规则已开放、异常可恢复或用户可顺利完成任务。
>
> **当前结论**：本轮已对设计文档做 v6.2 口径收敛；未在本轮独立完成运行时、接口、真机与用户测试，因此下表不得把“设计已覆盖”推导成“实现已完成”或“可用性已通过”。
>
> **状态字段**：订单验收必须分别核对履约 `service_state`、支付 `payment_state`、售后 `aftersale_state`、追加费用 `price_adjust_state`，以及服务端下发的 `allowed_actions`；任一轴未核验都不能写成订单闭环已通过。

## 0. 三条状态必须独立填写

| 维度 | 可用状态 | 判定依据 |
|------|----------|----------|
| 设计状态 | `未设计` / `草案` / `部分覆盖` / `已覆盖` / `需修订` / `不适用` | PRD 对应流程、入口、页面、状态、反馈、异常与文案均有明确规范，且无冲突 |
| 实现状态 | `未核验` / `未实现` / `部分实现` / `已实现` / `需修复` / `不适用` | 可运行产品中路由、权限、接口、数据、状态机、埋点与异常恢复均有可复现证据 |
| 可用性状态 | `未验收` / `不通过` / `部分通过` / `已通过` / `不适用` | 目标用户能在真机上独立完成关键任务，并达到成功率、时长、可理解性与无障碍标准；纯后台任务可标不适用但仍需运维验收 |

使用规则：

1. 三列分别评估，禁止用一个“已完成”覆盖三种含义。
2. 画布或 HTML 存在时，最多证明设计/原型存在；没有运行证据时，实现状态仍为 `未核验`。
3. 接口返回成功不等于用户可用；没有真机任务测试时，可用性状态仍为 `未验收`。
4. 只有“实现状态=`已实现`、可用性状态=`已通过`、服务端配置已开启”时，才可对外称功能正式可用。
5. 不再统计混合完成百分比；按功能逐项记录证据、缺口、负责人和复验日期。

## 7. 三道完成门槛

### 7.1 设计状态可标“已覆盖”

- 有唯一入口、目标与返回路径。
- 主流程、取消路径、权限与 `allowed_actions` 已说明。
- 页面八类状态、异步反馈、错误恢复和空态均有规范。
- 文案、角色、渠道、金额与状态语义不和 PRD 冲突。
- 已说明减少动态效果、触控区域、焦点、对比度与读屏标签。

### 7.2 实现状态可标“已实现”

- 真正路由可达，鉴权、角色与灰度配置正确。
- 接口、数据映射、多轴状态机与幂等策略可复现。
- 加载、空、部分失败、错误、离线、权限受限均可恢复。
- 异步任务离页后仍能查询，支付未知结果查询原交易。
- 日志、埋点、审计和关键告警可定位问题。
- 已有自动化/真机测试证据；静态 HTML 或画布不计为充分证据。

### 7.3 可用性状态可标“已通过”

- 用户与师傅分别用真实任务脚本完成主流程，无需旁人解释。
- 首次使用者能分清 AI 助手、订单聊天和人工客服。
- 能找到当前任务、角色切换、失败重试与求助入口。
- 能理解报价、追加费用、最终应付与支付结果，不产生“已同意即已扣款”的误解。
- 弱网、拒绝定位、超时、重复点击、后台切换和减少动态效果场景均通过。
- 验收记录包含设备、版本、账号角色、成功率、完成时长、问题与复验日期。

# 数据库迁移规范

Alembic 是已部署数据库结构的唯一迁移权威。首个受管基线 `59fdc7715893` 建立当时的 40 张表，后续显式迁移加入管理员审计和资金请求幂等表，当前 ORM 共 42 张表。实际 revision 链和 head 始终以 `server/alembic/versions/` 中受版本控制的文件及 `alembic heads` 的动态结果为准，不在文档中维护固定 head。

## 不可绕过的安全规则

1. 不在生产库上首次试跑迁移；先备份并恢复到隔离克隆，再在一次性 MySQL 8 环境完成真实升级。
2. 运行前核对目标环境、数据库名、主机和当前 revision。脚本与日志不得输出完整 DSN、密码、令牌或业务敏感原文。
3. 生产迁移必须有已验证备份、维护窗口、负责人、观察指标和前向修复方案；涉及资金/身份的数据迁移还必须有对账报告与异常清单。
4. 不使用 `Base.metadata.create_all` 作为生产迁移机制。
5. 不以 `alembic stamp` 掩盖结构漂移。`stamp` 只登记版本，不创建、不校验也不修改业务表。
6. 不在生产环境执行可能丢数据的自动 downgrade。回退优先关闭新读写开关并前向修复；若确需 downgrade，必须单独评审其数据后果。
7. 自动生成的 revision 必须人工检查类型转换、默认值、唯一约束、外键、索引、锁表时间、批量回填和 downgrade 行为。

## 新数据库

在 `server` 目录配置正常的数据库环境变量后运行：

```powershell
alembic upgrade head
alembic current
alembic check
```

当前自动化测试会在空 SQLite 数据库执行真实 `upgrade head`。发布前还必须在一次性 MySQL 8 数据库执行同一升级并检查表、索引、约束、字符集、金额精度和执行时间；仅生成 MySQL 离线 SQL 不等于完成真实验证。

## 已有但未纳入版本的数据库

旧开发库可能由 `Base.metadata.create_all` 创建，没有 `alembic_version`。首个 revision 会主动拒绝覆盖这类已有表。不要移除保护，也不要未经比对直接给线上库 stamp。

1. 备份源库，并恢复到隔离克隆。
2. 将应用数据库配置指向克隆，确认绝不是生产 DSN。
3. 对克隆记录基线：

   ```powershell
   alembic stamp 59fdc7715893
   alembic check
   ```

4. `alembic check` 必须报告 `No new upgrade operations detected`。若有差异，创建并评审显式的“旧结构 → 当前结构”迁移，不能继续 stamp。
5. 对克隆执行数据量、约束、孤儿记录、金额和关键订单抽样校验。
6. 只有克隆结构完全等价且演练通过，才可在有备份的生产库维护窗口重复同一基线登记。

## 创建后续 revision

```powershell
alembic revision --autogenerate -m "describe the schema change"
alembic upgrade head
alembic check
```

revision 应保持单一、可解释的业务目的。结构变更和大规模数据回填必要时拆分，以缩短锁表时间并允许独立校验。任何数据修复都应幂等：重复执行或中断恢复不得重复入账、重复合并账号或重复生成业务事件。

## v6.2 迁移顺序

以下是目标范围，不代表当前 revision 已包含：

| 阶段 | 迁移对象 | 必要保护 |
|---|---|---|
| 1. 统一身份 | 稳定账号主键、用户/师傅档案关联、角色可用状态、令牌版本 | 以受信身份建立候选匹配；重复/冲突 OpenID、UnionID 和孤儿档案进入人工清单，不自动猜测合并 |
| 2. 多轴状态 | `service_state`、`payment_state`、`aftersale_state`、`price_adjust_state`、对象版本 | 先加可空结构，影子回填并与旧 `Order.status` 对账，再双写和加约束；保留兼容投影 |
| 3. 报价与准入 | 报价状态/版本/截止时间、资格策略版本及必要快照 | 回填 `is_selected` 时保证每单至多一个 `selected`；不确定的历史终态留迁移报告 |
| 4. 位置会话 | 订单追踪会话、序号、会话版本、停止原因 | 新行程启用会话；历史轨迹不伪造实时会话，保留只读来源关联 |
| 5. 资金账本 | 结算分录、资金桶、支付/退款/提现关联、费率快照 | 切换前完成余额、交易、支付/退款、提现、保证金对账；差异不得通过修改总余额静默抹平 |
| 6. 可靠性 | 幂等记录、领域事件/发件箱、强类型消息深链 | 唯一约束兜住并发；旧消息提供兜底，不伪造无法确定的对象版本 |
| 7. 隐私审计 | 敏感操作审计、访问原因、脱敏摘要、保留策略字段 | 迁移日志不打印手机号、地址、证件、原始坐标、聊天或证据；管理员数据访问可追溯 |

推荐每个阶段遵循：`新增结构 → 小批回填 → 一致性报告 → 影子读/双写 → 加强约束 → 切换读取 → 稳定观察`。不得把所有高风险变化塞进一个不可观察的大 revision。

## 必要迁移测试

每个 revision 至少覆盖与其风险相称的测试：

- 空 SQLite 数据库 `upgrade head`，并用 `alembic check` 证明 ORM 无漂移；
- 旧的未版本化结构保护，确保失败时原表不被修改；
- MySQL 离线 SQL 可生成，以及一次性 MySQL 8 数据库的真实升级；
- 从上一 revision 升级到 `head`，关键数据数量、唯一约束、外键和索引正确；
- 中途失败后可安全恢复，回填重复执行不产生第二次业务效果；
- 身份迁移覆盖同账号双档案、仅单角色、重复身份标识、空标识和冲突标识；
- 状态迁移覆盖旧 `paid/reviewed/cancelled`、支付/退款并存、多条差价和售后处理中；
- 资金迁移逐主体、逐订单守恒，舍入差异为零或进入有责任人的异常清单；
- 位置、消息和审计迁移不扩大数据可见范围，不把敏感原文写入输出或日志。

## 发布前检查清单

- [ ] revision 链只有一个预期 `head`，应用版本与目标 revision 已绑定
- [ ] 备份恢复演练成功，克隆与一次性 MySQL 8 升级成功
- [ ] 自动生成操作逐项人工确认，无意外删除、缩窄或全表非空回填
- [ ] 估算锁表/回填时间，长任务可分批、可监控、可续跑
- [ ] 身份、状态和资金回填报告已签字，异常均有处置人
- [ ] 新旧读写兼容、功能开关和前向修复步骤已演练
- [ ] 回归测试通过，日志中无凭据、DSN 或业务敏感原文
- [ ] 迁移后执行 `alembic current`、`alembic check`、关键业务冒烟和资金对账
